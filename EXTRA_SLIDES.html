Slide 2 — Non-Functional Requirements

NFR-001 to NFR-007 — Proof in Code

NFR-001 Maintainability

Separate files each with one job:
models.py views.py forms.py templates/
Nothing mixed together.

NFR-002 Testability

17 automated tests in tests.py.
Run: python manage.py test clinic
Result: 17 passed in 0.090s

NFR-003 Reliability

Every view uses:
get_object_or_404()
Wrong URL → clean 404 page. App never crashes.

NFR-004 Security

@login_required on all owner views.
{% csrf_token %} on every form.
Session expires on browser close.

NFR-005 Observability

Django logs every request to terminal:
GET /owners/ 200
POST /owners/new/ 302
Real-time visibility.

NFR-006 Performance

prefetch_related('specialties') in vet view. One database call instead of one per vet. Prevents N+1 query problem.

NFR-007 Documentation → README.md + ARCHITECTURE.md + API.md + AI_USAGE.md — all in GitHub repo.

Slide 3 — Architecture Decision

Why I Chose Python + Django

🎯 Right Tool for the Context

The challenge allowed any technology stack. Choosing the right tool for the scope, timeline, and team is an architectural decision — not a developer decision. This was my BA call.

⚡ Batteries Included

Django comes with admin panel, ORM, authentication, forms, and URL routing built in. No extra libraries needed. Less code to write = fewer bugs = faster delivery.

🗄️ SQLite = Zero Setup

No database server to install or configure. The database is one file. Anyone can clone the repo and run it immediately. Perfect for a one-day build and demo.

📖 Readable Code

Python reads almost like English. AI-generated code was easy to review, understand, and validate. I could explain every line — which is the requirement: human judgment, not blind trust.

"Java + Spring Boot would have worked. But Django delivered the same result in half the time with less complexity. That trade-off decision is architecture."
