SDLC Stage 1 — Requirements

How I Read the Requirements

As a PM, my first job is to understand WHAT needs to be built before HOW. I mapped every requirement to a concrete deliverable.

FR-001 Owner Management

→ Owner model + list page + search + create + edit pages

FR-002 Pet Management

→ Pet model linked to Owner + add pet form + view history

FR-003 Pet Types

→ Separate PetType model (Dog, Cat, Bird, Hamster) — configurable without code changes

FR-004 Veterinarian Management

→ Vet model + Specialty model (many-to-many) + vets list page

FR-005 Visit Management

→ Visit model + schedule visit form + visit history on owner detail page

FR-006 Search & Navigation

→ Search bar on owners page + navigation bar on every page + pet lookup via owner

SDLC Stage 2 — Architecture

Why Python + Django?

The challenge allowed any technology stack. This was my deliberate architectural decision — not an AI decision.

  • ✓
    Django is "batteries included" — admin panel, database ORM, user auth, forms all built-in. Less code to write, fewer bugs.
  • ✓
    Python is readable — AI-generated code is easy to understand and validate. I can explain every line.
  • ✓
    SQLite requires zero setup — database is one file. Anyone can clone and run immediately.
  • ✓
    One-day timeline — Django delivers working features faster than Java + Spring Boot for this scope.

Java + Spring Boot

Original Spring PetClinic stack. More verbose, longer setup, less suitable for a one-day solo build.

Python + Django ✓ Chosen

Readable, fast, full-featured. Right tool for this project scope and timeline.

"Choosing the right tool for the context IS architectural thinking."

name, birth_date

→ Owner (FK)

Specialty

name
(Radiology / Surgery / Dentistry)

Vet

first_name, last_name
→ Specialties (Many-to-Many)

Visit

visit_date, description
→ Pet (FK)
→ Vet (FK)

As a PM I now understand: every feature request must be traced back to a database table. "Add blood type?" → one new field. "Track which nurse called?" → one new field with a FK. This thinking makes me a better PM in developer conversations.

Engineering Discipline

Clean Code Structure

Each file has exactly one job. This is the Django MTV pattern — separation of concerns.

  • ▸
    models.py — database table definitions only
  • ▸
    views.py — page logic only, no HTML
  • ▸
    forms.py — input validation only
  • ▸
    admin.py — admin panel config only
  • ▸
    urls.py — URL routing only
  • ▸
    templates/ — HTML only, extends base.html
  • ▸
    requirements.txt — dependencies documented

Lessons Learned

What I Learned as a PM Who Coded

📐 Requirements drive everything

Every page, every database field, every button exists because of a requirement. If I had skipped reading FR-001 to FR-006 carefully, I would have built the wrong thing — fast.

🗄️ Database design is the foundation

Before writing code, I designed 6 tables and their relationships. When the database is right, the code almost writes itself. When it's wrong, nothing works.

🤖 AI is a force multiplier — not a replacement

AI wrote code in seconds. But without my requirement interpretation and architectural decisions, that code would have solved the wrong problem.

🧪 Tests are proof, not optional

17 automated tests give me confidence to say the app works — not just "I think it works." This is measurable delivery quality.
