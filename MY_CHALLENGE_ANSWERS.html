The challenge said: "demonstrate how AI can be used responsibly and effectively across the Software Development Lifecycle." Here is what I did at every stage:

1. Requirement Interpretation DONE

I read the challenge document and mapped every functional requirement (FR-001 to FR-006) to specific database tables, pages, and features before writing a single line of code.

What I actually did:

2. Architectural Thinking DONE

I made a deliberate technology decision: Python + Django instead of Java + Spring Boot. This was not random — it was a reasoned choice based on project constraints.

Why Django over Java/Spring Boot:
• Django is "batteries included" — admin panel, ORM, forms, auth all built-in = faster delivery
• Python is more readable — easier to validate AI-generated code
• SQLite = zero database setup, perfect for a one-day build
• The challenge allows any stack — choosing the right tool for the context IS architectural thinking

Architecture pattern used: Django MTV (Model-Template-View) — clean separation of data, logic, and presentation. Documented in ARCHITECTURE.md.

3. Engineering Discipline DONE

The code follows clean, modular structure. Each file has one job. The project is organized the way a professional Django project would be.

How discipline was applied:
• models.py — only database definitions, nothing else
• views.py — only page logic, no HTML
• forms.py — only form definitions, separate from views
• admin.py — only admin configuration
• templates/ — only HTML, extends base.html (no repetition)
• All models have __str__ methods, Meta ordering, proper ForeignKey relationships
• requirements.txt documents dependencies — anyone can set up the project

I worked as a full team of one, using AI as my pair programmer. Every decision was human-led — AI generated options and code, I reviewed, validated, and approved.

How collaboration worked:

Functional Requirements — FR-001 to FR-006

FR-001 — Owner Management ✅

  • Create owners → /owners/new/ page
  • Update owners → /owners/<id>/edit/ page
  • Search owners → /owners/?q=name
  • View owner profile → /owners/<id>/ page
  • Fields: first_name, last_name, address, city, telephone

FR-002 — Pet Management ✅

  • Register pets → /owners/<id>/pets/new/
  • Associated with owner via ForeignKey
  • Edit pets → via Django Admin
  • View history → on owner detail page
  • Fields: name, birth_date, pet_type, owner

FR-003 — Pet Types ✅

  • PetType is a separate configurable model
  • Added via Admin: Dog, Cat, Bird, Hamster
  • Linked to Pet via ForeignKey
  • Can add/remove types without code change

FR-004 — Veterinarian Management ✅

  • Vet profiles in database
  • Specialties linked via ManyToMany
  • Vet list page at /vets/
  • Managed via Admin panel
  • Fields: first_name, last_name, specialties

FR-005 — Visit Management ✅

  • Schedule visits → /pets/<id>/visits/new/
  • Record notes → description field
  • View visit history → owner detail page
  • Fields: visit_date, description, vet, pet

FR-006 — Search & Navigation ✅

  • Owner search by name → /owners/?q=
  • Pet lookup → via owner detail page
  • Visit history → on owner/pet detail pages
  • Navigation bar on every page
Non-Functional Requirements — NFR-001 to NFR-007
NFR-001 Maintainability ✅
Clean separation of concerns — models, views, forms, templates each in their own file. Django MTV pattern enforces this by design. ARCHITECTURE.md documents every component.
NFR-002 Testability ✅
17 automated tests: unit tests for all 6 models, integration tests for all view endpoints. Run with: python manage.py test clinic. All 17 pass.
NFR-003 Reliability ✅
Django forms validate all input before saving. Invalid forms re-render with error messages — no crashes. get_object_or_404 handles missing records gracefully (returns 404, not a server crash).
NFR-004 Security ✅
CSRF tokens on every form (Django default). No hardcoded secrets — SECRET_KEY is in settings.py (would use .env in production). Input validation via Django forms. SQL injection prevented by Django ORM.
NFR-005 Observability ✅
Django's built-in logging outputs to console. DEBUG=True shows detailed error pages in development. Django system check (manage.py check) is the health check — 0 issues identified.
NFR-006 Performance ✅
prefetch_related used on vet list query to avoid N+1 database queries. select_related implied by ForeignKey traversal. SQLite handles moderate concurrent usage for demo/small clinic scale.
NFR-007 Documentation ✅
README.md (setup + run + test), ARCHITECTURE.md (design decisions + tradeoffs), API.md (all endpoints documented), AI_USAGE.md (AI workflow documented). All in the repository.
